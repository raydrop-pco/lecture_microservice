# Microservices 101-05: API Design for Evolution（API の進化的設計）

クライアントに影響を及ぼさずにコントラクトを進化させる

## 1. はじめに

モジュール 1 では、冪等性と結果整合性によって、障害が発生しても個々の処理を安全に実行する方法を学びました。モジュール 2 では、障害に備えた設計と、問題を素早く発見するための可観測性を扱いました。モジュール 3 ではデータ境界とオーナーシップを、モジュール 4 ではアプリケーション層のコミュニケーションモデルとワークフローコーディネーションのパターンを扱いました。モジュール 5 では**コントラクト層**に焦点を当てます。

モジュール 4 の結合タイプのセクションで、**「振る舞い的結合（Behavioral Coupling）」**を紹介しました。サービス利用者（クライアント）は利用するサービスが起動しているかどうかだけでなく、稼働時の振る舞いそのものに依存しています。例えばレスポンス内容のセマンティクス（意味）やデフォルト値、エラーをどう扱うかなどです。こうした振る舞い的結合は暗黙的なので把握しづらく、時間の経過とともに互換性のリスクになります。

**API コントラクト**とは、サービス提供者とコンシューマーがどのように相互作用するかを定める、正式で共有された「合意」のことを指し、以下のようなことを定義します。

* やり取りするデータはどんな内容か（スキーマや構造）。
* リクエストのやりとりの方法（プロトコルとメソッド）。
* データ型や必須項目、エラーなど、振る舞いに関する期待。

サービス間の「契約書」のようなものと考えてください。サービス提供者がこのコントラクトを守っている限り、サービス利用者は内部実装の詳細を知らなくても、サービスを信頼して利用できます。

サービスが自身の所有するデータを API を介して公開するようになると、新たなリスクが生まれます。それが **API の進化**です。フィールド名は変わり、エンドポイントは置き換えられ、振る舞いは修正されます。モノリスでは一度デプロイすれば、すべての呼び出し元が同時に変更を受け取ります。分散システムでは、サーバーとコンシューマーは独立したスケジュールでデプロイされます。モバイルアプリ、サードパーティ統合、組み込みデバイスなどのコンシューマーは、こちらの都合どおりにアップグレードしてくれないことがあります。

このモジュールでは、公開済み API を計画的に進化させる方法を学びます。移行中の互換性を保つためのテクニックと、古い動作を削除する前に安全性を検証するための運用手法を扱います。

> 💡 大事なことは「どのような変更をしたか」ではなく、「変更のロールアウト中／後とも、新旧どちらのバージョンのクライアントとも動き続けられているかどうか」です。

### このモジュールのメンタルモデル

モノリスの世界では、ステークホルダーとの長い調整や同期リリースによって、変更のリスクからコンシューマーを守ってきました。言い換えると「速度を犠牲にして安全を得る」運用です。分散アーキテクチャの世界に同じメンタルモデルを持ち込むと、調整コストが膨らみ、デプロイ速度もすぐに失速します。だからこそ、発想を「リリース時期の交渉」から「新旧の共存を前提にした設計」へ切り替える必要があります。

この転換が重要なのは、マイクロサービスの価値が「独立した変更とリリース」にあるからです。コントラクトを共存前提で設計していれば、API の利用者全員に同時アップグレードを強制することなく、チームが素早く改善を続けられるのです。

## 2. 互換性 101 — クライアントを破壊的な影響をもたらすものは何か

### API コントラクトの目的

API コントラクトというと、OpenAPI スペックや Protobuf ファイルを思い浮かべるかもしれませんが、それだけではなく、**クライアントが知るべきもの、見ているもの、依存するものすべて**です — ドキュメント化されていない動作も含みます。例えば、スペック上は nullable とされていても、実際には null の値が入ることのないフィールドがあれば、暗黙のコントラクトになります。ソート順が明示されていなくても、常にソートされたリストを返すレスポンスがあれば、それも暗黙のコントラクトになります。API コントラクトは、振る舞い的結合のリスクを軽減するものであり、チームが互換性管理、テスト、変更のリリースにおける可観測性を通じて継続的に維持管理している場合には、その効果を発揮します。

互換性とは：**既存のクライアントが（暗黙のルールも含めて）変更なしで動作し続けられること**です。

### 変更の分類

変更といってもすべてが同じリスクを持つわけではありません。まずは変更を正しく分類することが、安全な変更管理の第一歩です。

| カテゴリ | 説明 | リスクレベル |
|---|---|---|
| **追加的変更（Additive Changes）** | 新しい*オプション*フィールドの追加、新しいエンドポイントの追加、新しい enum 値の追加 | 通常は安全（ただし switch ロジックでの enum 処理には注意） |
| **意味的変更（Semantic Changes）** | 同じフィールド名で意味が変わる、nullable 性の変更、デフォルト値の変更、エラーの内容やステータスコードの意味の変更 | **危険** — 一見するとスキーマは変わらないのに、クライアントのロジックには影響がある |
| **破壊的変更（Breaking Changes）** | フィールドの削除、フィールドの改名、リクエストへの必須フィールドの追加、レスポンスフォーマットの変更 | **破壊** - 既存のクライアントは即座にエラー |

例えば、これまで `user_id` だったフィールド名を本来の意味に沿う `account_id` へと改名したとしましょう。これは**破壊的変更**になります。古いフィールドは消えてしまうので、`user_id` を読み続けているクライアントは `null` に遭遇することになり、もし null ガードをしていなければクラッシュしてしまいます。

本来は変更後のほうが正しいと思われる変更は特に（変更する側がよかれと思っているだけに）、トラブルになることが多いです：
* もともと Nullable として定義していた項目だが実際には null 値が入ることは業務的にこれまでなかった。仕様変更で null があり得るようになった。提供側は「もともと Nullable として定義していたのだから大丈夫なはず」とリリースしたが、クライアント側は null チェックをしていなかったためにクラッシュ。
* 「該当データなし」場合に、ステータスコード `200` でレスポンスボディを `{}` として返却していた。標準に合わせるべきだろうと、レスポンスコード `404` で応答するように変更したが、クライアントは `404` をチェックしていなかった。 
* 変更で新規フィールドを応答に追加することになった。以前の変更で廃止になったフィールド名をもう大丈夫だろうと再利用したところ、まだそのフィールド名のロジックが残っているクライアントがいて、想定外の挙動になってしまった。

エンドポイントやリクエスト値レスポンス値が明確に変わる変更以上に、同じ URL、同じフィールド値のまま意味を変えてしまうケースが実は一番危険です。

私たちはつい「利用者はドキュメントや変更通知を読んでいるはず」「変更期限を知らせたら、それまでに対応してくれているはず」と期待してしまいがちですが、残念ながら現実のクライアント開発者の多くは定義されている仕様よりも「実環境での振る舞い」を正として開発していることが多いものです。実世界での動作そのものがコントラクトを形成しているのです。

このような破壊的変更を避けるには、一度で置き換えずに、次のような段階的な移行パターンを適用します。

## 3. Expand & Contract — ゼロ・ダウンタイム移行パターン

Expand & Contract パターンで変更を 3 フェーズで適用していきます。変更要求の内容が*破壊的*な場合、つまり一度のデプロイでクライアントが動かなくる可能性がある変更の場合に、段階的に適用することで影響を回避でます。

### 3 つのフェーズ

```
フェーズ 1 — EXPAND（拡張）    フェーズ 2 — TRANSITION（移行）    フェーズ 3 — CONTRACT（縮小）

サーバー応答:                サーバー応答:                     サーバー応答:
  user_id  ← 旧フィールド        user_id  ← 旧フィールド              account_id ← 新フィールド
  account_id ← 新フィールド      account_id ← 新フィールド
                                                                   旧フィールド削除完了 ✓
旧クライアント: 読み取る         旧クライアント: 変更対応
  user_id ✓                     → account_id ✓
新クライアント: 読み取る
  account_id ✓
```

**フェーズ 1 — Expand（拡張）：**
- 古いものと並行して新しいフィールドや動作を追加する
- 新旧がレスポンスに併存する — クライアントの変更対応は必須ではない
- この段階では純粋な追加的変更なので、安全

**フェーズ 2 — Transition（移行）：**
- コンシューマー側が、新フィールドを参照するように更新する
- ドキュメント、`Deprecation:` と `Sunset:` レスポンスヘッダー、既知のコンシューマーへの連絡を通じて旧フィールドの廃止予定を通知する
- **移行を計測する**：本番環境でコンシューマー別・フィールド別の使用状況を追跡する
- 移行完了シグナルを定義する：ログやメトリクスで `user_id` の読み取りがゼロになったことをどのように検知できるかを設計
- 一定期間はこの新旧混在バージョンのクライアントをサポートする

**フェーズ 3 — Contract（縮小）：**
- おおよそのコンシューマーが移行したことを示す**確証**が得られたら、旧フィールドを削除する
- 廃止日付はあくまで計画の目安として扱い、削除基準とはしない。廃止の影響が極小化されたとデータで確認できたときに移行を進める。
- メモ：ここでの「Contract」は、インターフェーからレガシーフィールドを除去すること=インターフェースの縮小、という意味です。「API コントラクト（契約、合意）」と同じ英単語ですが意味が異なります。

### 最も重要なステップは「計測」

フェーズ 1（Expand）を実行するのは簡単です。その後、フェーズ 2 の期間にクライアントの移行状況を計測できるメカニズムがないと、チームはフェーズ 3（Contract）に移行する勇気を失ってしまいます。「とりあえず旧フィールドも残したままにしておこう」と廃止を先送りにしておくのを何度も見てきました。これを繰り返すうちに古いフィールドが残存し、API は過去の変更履歴を陳列するようなインターフェースを持つことになってしまいます。新しい開発者がスキーマを読んでも、どのフィールドが現行のものでどれが「念のため」残っているのか判断できません。

計測が難しいのはなぜか - **サーバーはクライアントがどの JSON フィールドを読んでいるかを直接観察できないから**です。レスポンスの中の新旧のフィールドのうちどちらかをクライアントは選んでいるわけですが、サーバー側に「こちらを使った」とは教えてくれません。クライアントの協力なしに、サーバーサイドでクライアントの挙動を推測しなくてはならない点に難しさがあります。

**サーバーサイドで推測可能なシグナル：**

| シグナル | 仕組み |
|---|---|
| **クライアントバージョンを推測（Version Inference）** | バージョン識別子（例：`/v1` -> `/v2`、バージョンヘッダー/メディアタイプ、または User-Agent/API キー/OAuth クライアント ID によるクライアントバージョン）を既知のフィールド使用法にマッピングします。旧バージョンのトラフィックがゼロになった時点で、次フェーズに安全に移行できる |
| **動作を推測（Behavioral Inference）** | 新しいフィールドがその後のリクエストのパラメータとしても現れる場合、クライアントが移行済みと推測できる |
| **カナリア戦略（Canary Omission）** | 一部のトラフィックのみ、古いフィールドの送信を一時的に停止するようにする。クライアントからのエラー問い合わせがゼロならば準備完了と推測できる |
| **コンシューマーレジストリ（Consumer Registry）** | サービス利用者の情報、そのバージョン、移行状況を組織的に追跡できるように API を設計しておく |

バージョニングについては、セクション 6 で解説します。どのバージョン管理戦略を採用する場合でも、バージョンレベルのトラフィックは、移行フェーズから縮小フェーズへのシグナルとなります。

明確にバージョン管理するか、最初からコンシューマレジストリを実装しておかない限り、クライアントの移行状況は状況証拠に頼るしかありません。勘頼みにならないように、明示的な移行基準を定義して継続的に追跡しておきましょう。例えば、**ゲートルール** として「本番環境のすべてのコンシューマーから 14 日以上連続でレガシーフィールド依存シグナルがゼロだと確認できたら、廃止基準を通過とみなす」といったものです。

### ウォークスルー：`user_id` → `account_id`

| フェーズ | サーバーが返す | 旧クライアント | 新クライアント | アクション |
|---|---|---|---|---|
| 変更前 | `user_id` | `user_id` を読む ✓ | — | — |
| Expand | `user_id` + `account_id` | `user_id` を読む ✓ | `account_id` を読む ✓ | サーバーをデプロイ |
| Transition | `user_id` + `account_id` | `account_id` に移行 ✓ | `account_id` を読む ✓ | クライアントを更新・監視 |
| Contract | `account_id` | *（移行済み）* ✓ | `account_id` を読む ✓ | サーバーから `user_id` を削除 |

サーバーは 2 回の独立したデプロイを行います。それぞれのデプロイ時点で後方互換性が保たれています。フェーズ 3 のゲートは可観測性の問いであり、カレンダーの問いではありません。

**フェーズ 3 の削除のための前提条件：**
- バージョン推測で、レガシー依存クライアントバージョンからのトラフィックが 14 日以上ゼロであること
- カナリア省略テストが残存コンシューマーに対してエラーなしで通過すること
- 廃止期間が経過していること
- 既知のコンシューマーがレジストリまたは直接確認で移行済みと確認されていること
- 削除後：24 時間のロールバックウィンドウ中にエラーレートを監視する

## 4. 意図的に破壊的変更を使う

ここまで、いかにクライアントに影響を与えずに API をアップデートするべきかについて考えてきました — これは最優先ではありますが、セキュリティやコンプライアンス、長期的なプラットフォームの健全性を損なわずに後方互換性を保つことが難しいケースもあります。

**互換性の維持をまず考えるべきですが、それ以外の選択が悪なわけではありません。**

過去に私自身が経験した、破壊的変更の実際の事例を紹介します。

| 事例 | 短期的コスト | 長期的利益 |
|---|---|---|
| **Google OAuth セキュリティ強化（2017〜2022 年）** | すべての OAuth コンシューマーに移行を要求 | セキュリティ態勢の向上、エコシステムの健全化、安全でない認可タイプの廃止 |
| **LINE API プラットフォーム刷新（2016 年 9 月）** | 全開発者に強制移行（BOT API → Messaging API v2） | スケーラビリティの向上、機能の充実、プラットフォームの刷新 |

Google のケースは、変更までの移行期間が確保されていたものの、その分先送りされ、期限ギリギリに既に稼働していた多くの API を修正しなくてはならなくなりました。LINE のケースは移行期間が半年ほどしかなく、ちょうど廃止予定の BOT API で開発テストを終えたばかりのアプリケーションを全て修正しなくてはならなくなりました。どちらのケースも、お客様の要求でもなく、開発ベンダーの瑕疵でもなく、修正のコストを誰が負担するのか、本当に必要なのか（なんとか抜け道はないのか）などの交渉が大変でした。

印象的だったのは LINE の開発チームがお客様を訪問して必要性と重要性を何度も説明してくれたことです。破壊的変更は痛みを伴いますが、提供ベンダー側の「最終的には顧客の利益になることであり、責任を持ってガバナンスのある意思決定をしている」という強い意志を理解することができました。
（でも大変でしたけどね…）

### 正当な破壊的変更の判断基準

破壊的変更は、開発側の設計上の便宜を優先するものであってはいけません。サービス提供者として、ガバナンスされた例外的な措置の場合のみ、正当化されます。

特に B2B サービスの現場では、影響力の大きい顧客が移行に抵抗するかもしれません。その圧力は重要なフィードバックにはなりますが、それくらいで揺らぐ意思決定なら他の方法があるはずです。「優良顧客の移行がまだ終わっていない」は、事業上必要な変更を無期限に延期する理由にはなりません。一度、破壊的な変更することを決めたのであれば、その変更を遅らせることは、通常、将来においてより高コストでリスクの高いものになります。

## 5. API スタイルと進化ルール — REST vs. gRPC vs. GraphQL

API をどの方法で提供していても、互換性を維持して進化させる、というゴールは同じです。ですが、API スタイルによって**コントラクトの提供方法が異なる**ので、互換性ルールもそれぞれのスタイルに応じた形で考える必要があります。（REST API 以外の経験のない方は、この機会に他の API スタイルにも触れてみてください）

### REST — 暗黙のコントラクト

**通信フォーマット:** HTTP 経由の人間が判読できるプレーン テキスト (通常は JSON)。

**コントラクトの共有:** 通常は OpenAPI (Swagger) に文書化されていますが、HTTP と JSON はそれ自体ではそのコントラクトを強制しません。サーバーとクライアントは、実装と仕様を一致させるために共有規律を必要とします。この柔軟性は便利ですが、暗黙の契約が発生する可能性も高くなります。

**エラー検出:** 破損は実行時にのみ発生することがよくあります。たとえば、クライアントが依然として `{ "user_id": "100" }` を期待しているのに、サーバーが `{ "user_id": "100" }` を返し始めた場合、HTTP トランスポートは引き続き成功しますが、クライアント アプリケーションがペイロードを誤って解析するか、値を使用しようとすると失敗する可能性があります。

REST では、「契約」は多くの場合、文書化と観察された動作の組み合わせです。これにより、REST が柔軟になり、広く採用されるようになりますが、クライアントが明示的に約束されていない暗黙的なセマンティクス (ステータス コード、Nullability、デフォルト、ページネーションの癖) に依存しやすくなります。

**API 進化時の留意点：**
- フィールド追加は、クライアントが処理しないだけなので一般的には安全
- フィールド名の変更とフィールドの削除は、多くの場合は破壊的変更になるので避ける
- OpenAPI スペックを権威あるコントラクトとして扱うこと、CI で検証すること

```yaml
# 例：Expand フェーズ中は、新旧両方のフィールド（user_id, account_id）を返す
paths:
  /api/profile:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                properties:
                  user_id:
                    type: string
                    deprecated: true
                  account_id:
                    type: string
                  name:
                    type: string
```

### gRPC — 明示的なコントラクト

**通信フォーマット:** HTTP/2 上でプロトコルバッファ（バイナリシリアライズされたデータ）を使用します。コンパクトで機械処理に適していて高速ですが、JSON と違い人間にとっては形式です。ペイロードは `{ "user_id": 100 }` よりも `(1: 100)` に近い形式と思ってください。通信上の互換性は、フィールド名ではなく、フィールド番号と型に依存します。

**コントラクトの共有:** 共有の `.proto` IDL（インターフェース定義言語）ファイルで、メッセージタイプと RPC メソッドが定義されます。クライアントとサーバーのコードはこのスキーマから生成されるため、両者は同じ信頼できる情報源に基づいて動作します。

**エラー検出:** エラーは多くの場合、アプリケーション層が実行される前に検出されます。例えば、フィールドの型が間違っている場合や、クライアントがサーバーが公開していない RPC メソッドを呼び出した場合、gRPC はビジネスロジックに到達する前にリクエストを失敗させることができます。

gRPCでは、両者が厳密に型付けされたスキーマに合意します。重要な点として、protobufはフィールド名ではなくフィールド番号でフィールドをエンコードするため、RESTよりも安全なリファクタリングが可能です。

**API 進化時の留意点：**
- 廃止されたフィールド番号を再利用しない（フィールド 3 が `string` だったものを `int` のフィールド 3 として追加すると、古いデータはゴミとしてデコードされる）
- 削除したフィールド番号と名前は `reserved` としてマークし、誤って再利用しないようにする
- 追加の新フィールド（新しい番号）は REST 同様、安全

```proto
// Expand & Contract による改名完了後：
message UserProfile {
  reserved 1;
  reserved "user_id";       // フィールド番号 1 の誤った再利用を防ぐ

  string account_id = 2;
  string name = 3;
}
```

### GraphQL — コントラクトとしてのスキーマ

**通信フォーマット:** RESTと同様のプレーンテキスト形式。HTTP経由のGraphQLクエリとJSONレスポンス（テキストベースのリクエスト、JSONレスポンス）。

**コントラクトの共有:** 厳密なGraphQLスキーマ（イントロスペクト可能でツールから参照可能）。APIは、クライアントに対して利用可能なフィールド、型、操作を正確に通知します。

**不具合が発生する箇所:** エラーは多くの場合、アプリケーション層が実行される前に検出されます。クライアントがスキーマに存在しないフィールドを要求した場合、GraphQLはビジネスロジックが実行される前に検証時にクエリを拒否できます。

GraphQLは従来のモデルを逆転させます。クライアントはフィールドを明示的に要求し、サーバーはそのクエリに応答する必要があります。これにより、スキーマが中心となり、非推奨の情報を開発者に直接通知できるため、進化がより明確になります。

**API 進化時の留意点：**
- フィールドを削除する前に `@deprecated` でマークする — いきなり削除しないこと
- フィールドは安全に追加可能
- スキーマのイントロスペクションによって可視性を提供する

```graphql
type UserProfile {
  user_id: ID @deprecated(reason: "account_id を使用してください")
  account_id: ID!
  name: String!
}
```

### 比較：コントラクトの所在と進化ルール

| | REST | gRPC | GraphQL |
|---|---|---|---|
| コントラクトの共有 | 動作 + ドキュメント（OpenAPI） | `.proto` ファイル | スキーマ |
| プロトコル強制 | なし | フィールド番号 + `reserved` | 型システム + `@deprecated` |
| 最も安全な変更 | オプションフィールドの追加 | 新番号でフィールド追加 | フィールドまたは型の追加 |
| やりがちなミス | ドキュメント化されていない動作への前提 | 廃止フィールド番号の再利用 | フィールドの無言削除 |
| 廃止シグナル | ドキュメント / レスポンスヘッダー | コメント + `reserved` | `@deprecated` ディレクティブ（IDE 可視） |

**ディスカッション：** 自分たちのプロダクトでコントラクトがどのように定義されて共有されているか、変更時に十分に互換性の検討をしているか確認してみてください。

## 6. バージョニング戦略

API バージョニングは**ルーティングをサポートし、変更に対するガバナンスのためのツール**になります。古い動作と新しい動作をどのように並行して実行するか、そして誰がどの動作を使用しているかをどれだけ容易に把握できるかを支援します。バージョニングによって変更起因のトラブルを防ぐことはできませんが、互換性の維持（追加的な変更、非推奨期間、使用状況のテレメトリなど）がトラブルを防ぐ役割を果たします。

### URL パス・バージョニング

URL パスによるバージョニングは最もわかりやすいバージョンニング戦略です（例：/v1/users -> /v2/users）。サーバー側でもログとダッシュボードを使ってクライアントに利用されているバージョンを特定することができ、クライアント側も変更を明確に理解できます。ただし、このアプローチでは並行メンテナンスが必要になります。クライアントの移行が完了するまでの期間、新旧 2 バージョンのアプリを維持する必要があり、維持コストは上昇します。また頻繁にバージョンを更新すると、バージョンが乱立する事態を招くこともあります。

> *注* : どうしても互換性のない動作を共存させる必要がある場合にのみ `/vN` を使用してください。v1.1.1 のようなパッチバージョンも使うべきではありません。URL はルーティング識別子であり、リリースノートではありません。パッチバージョンやマイナーバージョンはバージョン管理の乱立を招き、クライアントがすべての小さなバージョンを追跡しなければならないという誤った認識を生み出します。URL はできるだけ安定させましょう。

### ヘッダーまたはメディアタイプによるバージョニング

ヘッダーまたはメディアタイプによるバージョニング（例： `Accept: application/vnd.api+json;version=2`）を利用すれば、URL 空間をクリーンに維持することができます。これにより、エンドポイントの安定性を維持しながら、複数の表現や動作に対応できます。ただし、デバッグの透明性が低く、可観測性やゲートウェイルーティングでは、バージョンごとにトラフィックをセグメント化するために追加の作業が必要になることがあります。クライアント側の運用が煩雑になる可能性もあります。

### クエリパラメータによるバージョニング

実用的な折衷策として、クエリパラメータによるバージョニング（例： `/users?api-version=2`）も採用されています。適用しやすく、ゲートウェイの背後で展開しやすいという利点がありますが、「オプション」として扱われて無視されてしまうる可能性もあります。異なるバージョン間でキャッシュされたレスポンスが共有されないよう、キャッシュレイヤーの扱いにも注意する必要があります。

### スキーマファーストの進化

明示的なバージョニングを採用しないパターンです。多くの成熟したシステム、特に gRPC や GraphQL（あるいは REST でもガバナンスが厳格に適用されている場合）、頻繁に明示的なバージョンアップをするのではなく、スキーマ優先の進化が好まれます。単一の「最新」インターフェースを維持し、付加的な変更と必須でないポリシーを活用して API を変更していきます。複数のバージョンを並行して維持稼働させる必要はなくなりますが、明確な互換性ルール、明確な非推奨期間、そして古いフィールドや動作が使用されなくなったことを証明するテレメトリといった規律が求められます。

### Tips

まずはスキーマファーストで変更をできるだけオプション扱いにできないかを検討し、互換性のない動作の新機能や、アップグレードを強制できない長期運用の外部クライアントがある場合にのみ、明示的なバージョニングを導入するようにしてください。

**バージョニングを導入する場合でも：**
- すべての新バージョンには、旧バージョンの廃止日を設ける（廃止日のないバージョンは永久に提供することを約束するのと同義）
- 本当に非互換な変更の場合のみ、バージョニングを適用する
- 戦略を立ててバージョニングする。そうしないと、複数バージョンが乱立したり、互換性規律がどんどん弱くなってしまう

## 7. ロールアウト安全性ツール

Expand & Contract パターンはどのように変更を適用するかを紹介しました。セクション 3 の EXPAND（拡張）-> TRANSITION（移行） -> CONTRACT（縮小） のパスの中で、クライアントの移行状況を示唆するシグナルと、縮小フェーズに移る（旧フィールドの削除）前に確認すべきゲートについて解説しましたが、ここではさらに運用レイヤーに焦点を当て、その証拠を本番環境で活用するためのツールとロールアウト制御について説明します。

**非推奨ポリシーとサンセットに関するコミュニケーション：**
- 明確な非推奨ポリシー（注意・警告の発行方法、最小サポート期間など）を公開する
- ドキュメント、変更履歴、レスポンスヘッダー、ターゲットを絞ったアウトリーチなどを活用し、早期かつ繰り返しコミュニケーションを行う
- B2B であれば、移行イベントをカスタマーサクセス活動として扱う。タイムラインを合意し、サポートを提供し、必要に応じてエスカレーションを行う

**顧客利用状況の可観測性（削除ゲート）：**
- 本番環境において、バージョン、フィールド、クライアントIDに基づいて顧客トラフィックを計測する
- 「使用頻度ゼロ」を削除の基準とするが、以下の点に注意する：
  - フォロー期間を定義する（例：「30日間読み取り回数ゼロ」）
  - ロングテールトラフィックや季節性トラフィックを考慮する
- 実際の使用状況を示すシグナルがないと、チームは互換性の負債を除去する勇気を持てないままになる

**機能フラグと選択的ロールアウト：**
- 新しい応答動作を、まずトラフィックのサブセット（例：10%）に公開
- 広範囲にロールアウトする前に、本番環境で新しい動作を検証する
- ロールアウトを開始する前に、成功シグナルとロールバックシグナルを定義する
- 影響範囲を制限する：新しい動作が正しくない場合は、すべてのコンシューマーに影響を与えることなくロールバックする

**機能フラグと選択的ロールアウト（リスクの高い動作変更の場合）：**
フィールド定義などスキーマが変更されていなくても、動作/セマンティクス（デフォルト値、ソート、丸め、認証）によってコンシューマーが動作しなくなる可能性がある。これらの点については、以下の点に留意する。

- 新しい動作はカナリアリリースでまず少数のユーザーグループに展開する（例：1% → 10% → 50% → 100%）
- 有効化する前に、成功基準とロールバック基準を定義する
  - エラー率／クライアントクラッシュ率
  - コンバージョン率またはビジネスKPI（該当する場合）
  - レイテンシ／タイムアウトの変更（新しい動作によって負荷が増加する可能性もある）
- ロールバックが迅速かつ安全であることを確認する

### カナリア・リリースとフィーチャーフラグ・ロールアウトの違い

**カナリアリリース**は、*デプロイメントベース*のロールアウトです。**2 つのサービスバージョン（旧バージョンと新バージョン）を同時に**実行し、本番環境のトラフィックのごく一部を新バージョンにルーティングします（例：1% → 10% → 50% → 100%）。シグナルに問題が見られた場合は、カナリアリリースからトラフィックを別のバージョンにルーティングするか、デプロイメントをロールバックすることで対応します。
- **メリット:** 実際のトラフィックで*全体*の新しいビルド（コード、設定、ランタイム）を検証できます。安全に切り替えられない変更（パフォーマンスの改善、依存関係のアップグレード、インフラの変更など）に適しています。
- **デメリット:** **異なるバージョンを混在させて運用する必要があります（互換性の問題、デバッグの複雑さ）。ロールバックに時間がかかる場合があります。トラフィックのセグメンテーションが適切に行われていない場合、ノイズが発生する可能性があります。

**フィーチャーフラグによるロールアウト**は、*動作ベース*のロールアウトです。通常、**デプロイ済みのバージョンは1つ**だけで済みます（新しいコードは既にリリース済み）。新しい動作は、少数のユーザー/テナント/リクエストに対してのみ有効になります。ロールバックはフラグをオフにするだけで済み、通常は再デプロイよりも高速です。
- **メリット:** ロールバックが高速（トグル操作）；コホートベースのロールアウトをサポート（テナント、ユーザー、リージョン別）；スキーマが変更されない**セマンティックな変更**（デフォルト値、ソート、丸め処理、認証動作など）に最適。
- **デメリット:** フラグは複雑さを増し、「永続的」になる可能性があります；両方のパスをテストする必要があります；管理されていない場合、フラグによって隠れた組み合わせ（「フラグの相互作用」）が発生する可能性があります。

**Tips:** 動作の変更をトグル操作で分離でき、ロールバックを高速に行いたい場合は、**フィーチャーフラグ**を使用しましょう。変更が、実行時に安全に無効にできない新しいバイナリ/ランタイム/インフラストラクチャの動作に関連している場合は、**カナリアリリース**を使用するほうが賢明です。


> モジュール 2 を思い出してみて：レジリエンシーを証明するための本番ツールとしての可観測性は、API 進化の可観測性としても適用できます。ここではシステム全体の健全性ではなくクライアントの移行状況を測定していますが、共通のメトリクスが使えることも多いです。

## 8. まとめ：意図を持って進化し、証拠を持って削除する

マイクロサービスの世界では、変化は絶え間なく続くものです。API を安定的に維持できれば理想的ですが、セキュリティ修正、プラットフォームの進化、あるいはドメインモデルの修正など、変化が避けられない場合もあります。そのとき、単にコードをどう更新するかだけではありません。分散システムの世界では、異なるバージョンの混在もまた、許容せざるを得ないものです。今日デプロイしたサーバー側のインターフェースやロジックが、クライアントに適用されるのは、それぞれのアップグレードのタイミングに依存します。古い動作と新しい動作が予想以上に長く共存することもよくあります。

安全に API を変更して進化させるためには、規律とエビデンスの両方が必要です。

**Expand & Contract**（まず追加し、後で削除する）パターンの遵守、**振る舞い的結合**による互換性をスキーマ互換性と同じくらい真剣に扱うこと、そして**ほんとうに互換性のないセマンティクスに対してのみバージョニング戦略**を適用することといった手法は、実践的な指針になります。

そして、**可観測性**、つまり明確な使用状況シグナル、コンシューマーごとの導入状況追跡、そして安全なロールアウトツールがなければ、移行を完了させてよいという確信が持てません。めざすところはシンプルです。変更をリスクではなくルーチン化し、それに依存するユーザーに影響を与えることなく API を進化させることです。

### 次のモジュールへ

このモジュールは*何を*安全に変更するか — コントラクトの進化、移行パターン、可観測性 — を扱いました。モジュール 6 ではそれらの変更を本番環境に安全にリリースする*方法*を扱います。

**モジュール 6（デプロイ安全性）**では、カナリアとブルーグリーンのリリース戦略、ランタイム安全性コントロールとしてのフィーチャーフラグ、ロールバック基準と爆発半径管理を扱います。

API の進化は何を安全に変更するかを定義します。デプロイ安全性はそれらの変更を安全にリリースする方法を定義します。変更がコントラクト上安全でも、ロールアウトの仕組みが誤っていれば障害を引き起こす可能性があります — 両方が必要です。

## 付録：本番対応チェックリスト

- [ ] すべての API 変更は実装開始前に「追加的・意味的・破壊的」に分類されている。
- [ ] 破壊的に見える変更は Expand & Contract パターンを使用する — 一度のステップでのフィールド削除・改名は行わない。
- [ ] サーバーサイドの監視が本番環境でコンシューマー別・フィールド別・バージョン別の使用状況を追跡している。
- [ ] フェーズ 3 開始前に移行完了シグナル（14 日以上のレガシーフィールド読み取りゼロ）が定義されている。
- [ ] 廃止予定はドキュメント、レスポンスヘッダー（`Deprecation:`、`Sunset:`）、コンシューマーへの直接連絡を通じて通知されている。
- [ ] REST：OpenAPI スペックが CI で検証され、権威あるコントラクトとして扱われている。
- [ ] gRPC：廃止されたフィールド番号と名前が `reserved` としてマークされている。フィールド番号は再利用しない。
- [ ] GraphQL：フィールドは削除前に `@deprecated` でマークされている。本番環境でのフィールド使用状況が監視されている。
- [ ] すべての新 API バージョンに前バージョンのコミット済みサンセット日がある。
- [ ] 破壊的変更は追加的パスが実行不可能で、移行パスと廃止期間が定義されている場合にのみ承認される。
- [ ] ロールアウトはフィーチャーフラグまたはカナリアデプロイを使用して爆発半径を制限する。成功とロールバックのシグナルはロールアウト開始前に定義されている。
